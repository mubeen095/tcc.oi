The same task, marked three ways.

A rubric proves nothing until you see it applied. Below is one Practitioner-level task answered at distinction, developing and not-yet level, with the reviewer notes that produced each mark.

What these are. Worked exemplars written by our assessment team to calibrate reviewers — not real candidate submissions. We label them this way because presenting invented candidates as real graduates is the exact behaviour this site exists to argue against.

The task

Support triage. A SaaS company receives 500 support tickets a week. Design an AI-assisted triage workflow. State where the model acts alone, where a human must confirm, how you would measure whether it is working, and what you would do when it fails.

Practitioner level · 60 minutes · role artifact 45 marks, judgement 25, applied knowledge 30

Exemplar A — distinction 91 / 100

Approach. Classify on arrival into four routing buckets, draft a first response for three of them, and escalate anything touching billing disputes or security to a human queue before a draft is generated at all.

Where the model acts alone: tagging, routing and internal summarisation. No customer-visible text is sent without a human pressing send, because the cost of one wrong refund promise exceeds the saving on a thousand correct drafts.

Measurement: first-response time, percentage of drafts sent without edit, re-open rate within seven days, and a weekly sample of 50 closed tickets read by a human. Re-open rate is the guardrail — speed without it just moves work downstream.

When it fails: if re-open rate rises above baseline for two consecutive weeks, the auto-draft is switched off for that bucket and the failures are read before the prompt is touched. Models fail in clusters, and clusters are diagnostic.

Artifact 43/45 · Judgement 24/25 · Applied knowledge 24/30

Reviewer note. Names the failure mode it is optimising against, and picks a guardrail that would actually catch it. Loses points only on model selection: it never says which class of model suits classification versus generation, or why.

Exemplar B — developing 62 / 100

Approach. Use an LLM to read each ticket, assign a category and priority, and draft a reply. Route low-priority tickets straight to the draft. Send high-priority tickets to a human.

Measurement: track accuracy of categorisation and customer satisfaction.

When it fails: retrain the model on the misclassified tickets.

Artifact 29/45 · Judgement 13/25 · Applied knowledge 20/30

Reviewer note. The shape is right and the writing is clear, which is why this passes. Three things cost it 29 marks. "Low priority" and "safe to answer automatically" are treated as the same thing, and they are not — a low-priority billing question is still a billing question. Accuracy is stated as a goal with no threshold, so the workflow has no switch. And "retrain the model" is not available to a support team, which means the failure plan is theoretical.

Exemplar C — not yet 38 / 100

Approach. Connect the ticketing system to ChatGPT with an API key. Let it answer all tickets automatically. This reduces workload by 80 percent and improves customer experience.

Measurement: number of tickets handled.

Artifact 14/45 · Judgement 6/25 · Applied knowledge 18/30

Reviewer note. Fails on the criterion that matters most, which is judgement. There is no human boundary on an irreversible action, no measurement that could detect harm, and a specific performance number with nothing behind it. Note that the applied-knowledge mark is not zero — the candidate knows what an API is. Knowing a tool and being trusted with it are different marks, and only the second one gets you hired.

What this is meant to show

Exemplar B is the one to read twice. It is fluent, plausible and wrong in three specific ways, and it still passes — because a pass means "employable with support", not "finished". A provider that only shows you distinction-level work is showing you its best day, not its standard.
